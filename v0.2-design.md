# v0.2 design: cascade scheduler and per-flow resequencer

**Status: built, deployed to both nodes and running in cascade mode** (2026-09-12). Sections
1-14 are the design as approved; **section 15 records what building it changed**, and where
the two disagree, section 15 is what the code does.

Read this before changing v0.2 code. It is written for the session that implements it: the
decisions below are settled with the project owner and are not to be re-litigated without
new field evidence. Where this document names a file, function or constant, it was checked
against the tree at tag `v0.1` (`3ddbf7d`); verify it still exists before relying on it.

**Naming.** Versions are v0.1, v0.2, ... What older documents call "v1" (`scope-v1.md`) is
v0.1, and what they call "v2" ("deferred to v2", D-009) is v0.2.

---

## 1. What v0.2 is

v0.1 places bulk **per flow**: each flow is hashed onto one path of a load-balancing set
(D-044 to D-046). A multi-flow transfer uses every healthy link, but one flow never exceeds
one link, and the call's path is protected by a binary gate that drops all bulk when that
path queues (D-031).

v0.2 places bulk **per packet**, in a **cascade**:

- **Order.** Bulk fills the highest-latency usable path first.
- **Spill.** Only when that path shows congestion does bulk spill onto the next
  lower-latency path, and so on down to the path carrying the call.
- **Resequence.** A resequencer at the far end puts each flow back in order before
  delivery.
- **Protect.** One continuous controller per path, reading the send-direction queue delay
  the peer reports, sets how much bulk each path may take. On the call's path that same
  controller is what protects the call.

The scheduler is the first part of v0.2. The v0.1 gaps listed in §12 follow it.

## 2. Settled decisions

| # | Decision | Source |
|---|---|---|
| S1 | The control loop is continuous, re-evaluated every scheduler tick, not a periodic re-weighting | owner |
| S2 | The reorder budget must be large enough to aggregate Starlink with an LTE link | owner |
| S3 | Bulk cascades: highest-latency path first, spilling to lower-latency paths only on congestion, so real-time and transactional stay responsive on the low-latency link | owner |
| S4 | Bulk **may** overflow onto the path carrying a live call | owner |
| S5 | Cascade order is **measured outbound latency** | owner |
| S6 | The spill trigger is send-direction queue delay (D-024), not the bandwidth estimate | owner |
| S7 | D-031's binary admission gate is **replaced** by the continuous controller, not kept as a backstop | owner |
| S8 | The design generalises to N paths from the start | owner |
| S9 | Resequencing uses a **per-flow-bucket sequence** carried on bulk packets, in a new wire version 3 | owner deferred to recommendation |
| S10 | Deploy to the nodes as soon as it passes tests; tune on the road rather than waiting for a field drive | owner |
| S11 | Real-time bypasses the resequencer (D-006 unchanged). Transactional never enters the cascade or the resequencer | draft, follows from S3 |
| S12 | **Real-time on a path never prevents or throttles bulk.** It changes only that path's place in the fill order (last) | owner, during implementation |

Two consequences of these that the implementer must not miss:

- **Transactional goes back to the primary alone.** In v0.1 `txFor` hashes transactional
  across the spread set together with bulk (see its comment). S3's goal is transactional
  on the low-latency link, so in cascade mode transactional returns to `txTrans`, the
  primary. It is small, it is TCP, and it stays single-path.
- **The controller is the only thing between a download and the call.** S4 plus S7 mean
  there is no second check on the call's path. §5.4 is therefore the most safety-critical
  code in v0.2, and D-031's pinned scenarios must be re-proven against it (§10).

## 3. Problems found in review, and how this design answers them

These came out of reviewing the first draft against the code. Each is handled in the
section named.

1. **`GlobalSeq` cannot be the resequencing key.** It is one counter across every packet
   of every class (`session.nextGlobalSeq`) and is also the dedup key (D-038). A bulk
   resequencer ordering on it would wait out a hold on every lost real-time or
   transactional packet, and one lost packet in one download would stall every other
   bulk flow. → Per-flow-bucket sequence, §4.
2. **Loss without queueing is invisible to a queue-delay trigger** (D-046: Starlink lost
   71% at the radio and never queued). With per-packet spreading, every such loss costs a
   hold timeout. → Loss is a congestion input to the controller (§5.4), and D-046's
   delivery gate still decides membership (§5.1).
3. **Two paths within a few milliseconds would swap order every tick** (measured 31.8 vs
   38.4 ms, and 30.5 vs 35.1 ms). → Order hysteresis, §5.2.
4. **Send-direction feedback arrives only once a second** (`report_interval_ms` = 1000).
   Worse, reports ride only standalone packets, which `dueForReport` sends only on a path
   that has been idle for `echo_interval_ms`. A cascade keeps every path busy, so reports
   would **stop entirely** exactly when the controller needs them. → §6.
5. **Late packets must be delivered, not dropped.** → Fail open, same rule as D-038, §7.
6. **Version negotiation would break a v2/v3 rolling upgrade.** `protocol.Parse` reads
   `flagCapable` as "the peer can read `Version`", meaning *this* build's newest version.
   A v3 build hearing a v2 build's capable bit would conclude the peer reads v3, emit v3,
   and the v2 peer rejects every packet with `ErrVersion`. That is a tunnel outage in
   the middle of an upgrade to a vehicle. → §4.1, and it is implementation step 1.
7. **The dedup window is too small for per-packet spreading at high packet rates.**
   `dedupBits` = 4096 was sized as "four seconds at a thousand packets a second". At
   ~30k pps a copy arriving 200 ms behind is ~6000 sequences back, so it fails open and a
   duplicated real-time packet would be delivered twice. → Raise to 65536 (8 KB), §4.3.

## 4. Wire format: version 3

### 4.1 Versioned capability (fix first)

The capability advertisement becomes versioned, using flags bit 6:

- bit 5 (`flagCapable`, existing): "I can read version 2".
- bit 6 (`flagCapableV3`, new): "I can read version 3".

A v3 build sets **both** bits on every packet. A v2 build sets only bit 5, and its parser
ignores bit 6. The negotiated version is the highest one the peer has advertised:

```
negotiated = packet version
if bit 5: negotiated = max(negotiated, 2)
if bit 6: negotiated = max(negotiated, 3)
```

Never "this build's `Version`". Bit 7 stays reserved for the next capability.

Test this both ways: a v3 build talking to a v2 build must settle on v2 at both ends, and
two v3 builds must settle on v3. Carry the existing `notePeerVersion` rule, that the
negotiated version never goes back down, forward unchanged.

### 4.2 Flow-bucket sequence field

It is present **only on version 3 packets of `TypeData` with class `ClassBulk`**, and it
is implied by those three fields rather than flagged. That keeps bit 7 free, and every
input to the rule is already on the wire and parsed before the field is reached.

```
base header, 15 bytes (unchanged)
flow-seq field, 4 bytes, big-endian, immediately after the base header when present
    bits 31-20   bucket id (0..4095)
    bits 19-0    sequence within that bucket, wrapping at 2^20
echo block (unchanged)
report block (unchanged)
auth tag (unchanged, covers the flow-seq field like every preceding byte)
```

- **Bucket on the wire, not recomputed at the receiver.** Both ends could compute the
  same `flowHash` from the same inner bytes. But if the hash ever differed between two
  builds during a rolling upgrade, sequences from different flows would interleave in one
  bucket and every packet would wait out a hold. That failure is silent and slow. Carrying
  the bucket makes the packet self-describing.
- **Sender.** `bucket = flowHash(payload) % 4096`, and `seq = flowSeq[bucket]++`. The table
  is 4096 `uint32`s owned by the single `readPayloads` goroutine, so it needs no locks.
  Two flows in one bucket share a sequence space: still correct, just marginally more
  head-of-line blocking.
- **20-bit sequence.** Serial arithmetic over 2^20 gives a ±524k-packet window, far beyond
  any reorder depth. The resequencer must use serial comparison; D-038 found that a plain
  `>` passes short tests and breaks after the wrap.

### 4.3 Budgets and constants

- `MaxDataHeaderLen` grows by 4 (`FlowSeqLen`). The recommended tunnel MTU drops from
  **1292 to 1288**, still 8 bytes above the 1280 floor (`minTunnelMTU`). **Both systemd
  units pass `-tun-mtu 1292` explicitly and must be changed to 1288 on deploy.** MSS
  clamping in `deploy/omp-tun-up` uses `rt mtu`, so it follows automatically.
- `dedupBits` goes from 4096 to 65536 (§3 item 7).
- **No cascade toward an old peer.** Per-packet spreading is used only once the peer is
  negotiated at ≥ 3. Toward a v2 peer, which has no resequencer, the sender stays in flow
  mode automatically: reordering a TCP flow into a receiver that cannot fix it is how
  D-044's first live test fell to 4 Mbps.

## 5. The cascade (sender)

Runs in `scheduler.evaluate` on every tick (`eval_interval_ms`, 200 ms), and publishes into
the immutable `decision` exactly as v0.1 does. Both ends run it independently for their
own send direction: home cascades downloads, the RV cascades uploads.

It is active only when all of these hold:

- `bulk_scheduler` is `cascade`
- the peer is negotiated at wire version ≥ 3
- the classifier is running (`scheduler.classifying`; below WireGuard everything is
  `ClassUnknown`, which is D-031's and D-033's trap)
- the scheduler is not in blind mode

Otherwise bulk behaves exactly as v0.1: `steerBulk`, the spread set and the D-031 gate.

### 5.1 Membership

- **Protected paths.** `d.tx`, meaning the primary plus any duplication or
  make-before-break target. These carry real-time and transactional traffic. They are
  **always members and always last** in the cascade (S4: bulk may overflow onto them).
- **Unprotected members.** The eligible paths that pass v0.1's spread tests, unchanged:
  not Red, `stateStable`, `deliveringForSpread` (R ≥ `spread_min_r` and not flapping) and
  not `undersizedForSpread`. No new membership test is added.
- **Delta gate** (`scope-v1.md`). An unprotected path whose outbound delay exceeds the
  primary's by more than `resequencer_max_hold_ms − resequencer_hold_margin_ms` is left
  out, because its packets would arrive after the resequencer had given up on them. With
  the defaults, a path may sit up to 190 ms behind the primary. That comfortably covers
  Starlink beside LTE (S2).
- **Forest canopy, D-033.** If no unprotected path qualifies, the D-033 steered path
  `steerBulk` would have picked (which may be unstable) takes the first slot. That
  preserves "use Starlink only for bulk" under canopy. It is still subject to the delta
  gate.

### 5.2 Order

- **Key.** Unprotected members are sorted by outbound delay, **descending**, using
  `scoringDelayMs(p, c)`, the same send-direction figure the ranking tie-break already
  uses (rttFloor/2 plus reported spread). Protected paths follow, in `d.tx` order.
- **Hysteresis.** Two adjacent members swap only when the one behind has been slower by
  more than `cascade_order_hysteresis_ms` for five consecutive ticks (one second). The
  order is scheduler state that persists across ticks, not recomputed from scratch. Swaps
  are logged.
- **Why order still matters with a resequencer.** A swap cannot reorder a flow past
  recovery, because the resequencer absorbs it, but it changes which link carries the
  load. Unstable ordering is the D-044 oscillation relocated.

### 5.3 Data path: per-path caps and token buckets

The decision publishes, per cascade member, `capKbps`, where 0 means **unlimited**. The
data path (`txFor`, bulk class) keeps one token bucket per member, owned by the
`readPayloads` goroutine alone:

```
refill:  tokens_i += cap_i/8 * elapsed, capped at max(cap_i/8 * 100 ms, 3000 bytes)
send:    walk members in cascade order; take the first with cap unlimited or
         tokens >= len(packet); subtract; send on that one path
none:    drop at the ingress; count bulk_throttled
```

- **Consequences.** The first member takes everything until its cap is set, which is S3
  exactly. Overflow spills in order. Dropping at the ingress when every cap is exhausted
  is D-031's mechanism, "let it queue at the ingress where it costs nothing", applied in
  proportion instead of all at once.
- **Other classes.** Real-time and transactional never touch the buckets and are never
  dropped. They count against a path only through the queue delay they cause.
- **Accounting.** The data path counts bulk bytes sent per path in atomics, which the
  evaluation reads as `bulkKbps_i`.

### 5.4 The per-path controller

One controller per cascade member, run every tick. Its inputs come from `pathMetric`:
`txQueueMs` (q), `txLoss` (l, percent), `haveTx` and the report's age, and `bulkKbps` (s).

- `T` = `cascade_queue_target_ms` for unprotected paths, `cascade_protected_queue_ms` for
  protected ones.
- `delivered = s × (1 − l/100)`, the same discount as D-050's `deliveredKbps`.

```
no report ever received on this path       -> cap = unlimited  (no evidence: do not throttle)
report older than 3 × cascade_report_interval,
  but not yet peerViewStale                -> hold cap          (evidence lapsed: do not grow)
report older than peerViewStale            -> cap = unlimited  (as "no report")

congested:  q > T  or  l >= cascade_loss_percent
    clean = 0
    f = clamp(1 − 0.5 × (q − T)/T, 0.5, 0.9)   if queue-triggered
    f = 0.8                                     if loss-triggered only
    if cap unlimited: cap = delivered           (seeded; see note on bwEstimate)
    else:             cap = min(cap, delivered) × f
    cap = max(cap, 64 kbps)

clean:      q <= T/2  and  l < cascade_loss_percent
    clean++
    need = cascade_recover_intervals, × 5 on a protected path
    if clean >= need and s >= 0.9 × cap:        (grow only a cap that is being used)
        cap = cap × 1.10 ; clean = 0
        if cap > 10 Gbps: cap = unlimited

otherwise (T/2 < q <= T): hold
```

What each part is for:

- **Proportional decrease.** Just over target costs 10%. At twice the target the cap
  halves. It never falls below 64 kbps, and on the call's path that floor is D-031's gate
  in the limit.
- **Asymmetric recovery**, carried over from D-031. Decrease happens on the first bad
  tick. Growth needs `cascade_recover_intervals` clean ticks, one second by default, and
  five times that on a protected path, which matches D-031's five seconds. Symmetric rules
  oscillate, and on the call's path every oscillation is a burst of queue through the
  call.
- **Growth only when demand-limited.** A cap nobody is pushing against is not evidence of
  headroom. It rises about 10% every second while in use, so 1 Mbps reaches 100 Mbps in
  roughly 50 s. Tune this on the road.
- **Loss as congestion.** This answers D-046. The threshold is deliberately well above
  ordinary cellular loss (a few percent) so random radio loss does not ratchet a healthy
  link down, which was cubic's failure in D-041. Links losing far more are already
  excluded by `deliveringForSpread`.
- **The bandwidth estimate** (`bwEstimate`, D-023/D-047–D-051) is not the control signal.
  Its only role is the seed: when a path first congests while unlimited, the cap is
  seeded from `min(delivered, limitKbps)` if `limitKbps > 0`. The controller then tracks
  capacity by itself, reactively and without probes, which is D-023's philosophy with a
  signal that has not needed five fixes.
- **Where the gains live.** 0.5, 0.9, 0.8, 1.10, × 5 and 64 kbps are named constants in
  code, not settings, until road data says one needs to move. That follows principle 2
  and the settings-pruning review already under way.
- **Logging.** Only transitions are logged: unlimited to capped, capped to unlimited, and
  the protected path entering or leaving throttle. The journal lives on the hardest box to
  reach.

## 6. Feedback cadence

The controller acts on the peer's report of our send direction. Two changes make that
report arrive when it is needed:

1. **Reports while receiving bulk.** A node that has received flow-seq bulk packets on any
   path in the last two seconds sends a standalone report every
   `cascade_report_interval_ms` (default 200) on **each path that carried bulk**,
   **regardless of whether that path is idle**. This bypasses `dueForReport`'s idle check
   for these packets only. One report covers every path (up to `MaxReportEntries`), so
   sending on several paths is redundancy, not duplication of content. The cost is about
   2.5 kbps per path.
2. **The ordinary cadence is unchanged** otherwise: `report_interval_ms` and the idle rule,
   so a quiet tunnel pays nothing new.

The report block format does not change. `QueueTenthMs` and `LossPerMille` already carry
what the controller reads.

## 7. The resequencer (receiver)

It sits on both ends' receive paths **after** `sess.deliver(h.GlobalSeq)` (dedup) and
before `local.write(payload)`. Only packets carrying a flow-seq field enter it. Everything
else is written straight through, exactly as today.

Per bucket, the state is:

- `next`, the sequence expected
- a buffer of out-of-order packets keyed by sequence, with their arrival times
- `gapSince`, when the oldest unfilled gap opened
- `lastSeen`

On each packet `s` for its bucket:

```
s == next      deliver; next++; drain consecutive buffered packets
s ahead        buffer (copy from a sync.Pool); if no gap open, gapSince = now
s behind       deliver immediately (fail open, D-038's rule); count late_delivered
|s − next| > 2^18 (serial)   treat as a sender restart: flush buffered in order, next = s + 1
```

A sweeper runs every 5 ms. For any bucket with `now − gapSince ≥ holdBudget`, it skips the
gap: `next` becomes the lowest buffered sequence, the consecutive run is delivered, and
`gaps_skipped` is counted. A bucket idle for 30 s is forgotten.

- **Never drops a packet.** A skipped gap is left for TCP to retransmit. A packet arriving
  after its gap was skipped is delivered as late. Principle 5, and D-002's "no queue
  layer": this is a bounded hold, not a queue.
- **Memory bound.** At most 16384 buffered packets in total (about 21 MB). When the bound
  is reached, the bucket with the oldest waiting gap is force-skipped. It never drops.
- **Hold budget.** Computed from the receiver's **own inbound** measurements. The receiver
  is measuring the very direction it is resequencing, so no wire field or clock sync is
  needed:

  ```
  over paths that delivered flow-seq packets in the last 2 s:
    slowest = max_i(rttFloor_i/2 + inboundSpreadP95_i)
    fastest = min_i(rttFloor_i/2)
    holdBudget = clamp(slowest − fastest + resequencer_hold_margin_ms,
                       resequencer_hold_margin_ms, resequencer_max_hold_ms)
  ```

  It is recomputed every tick. With one path active, nothing reorders and packets pass
  through as they arrive. The `late_delivered` rate is the road-tuning signal: persistent
  late deliveries mean the margin is too small.
- **Concurrency.** The initiator runs one `readLoop` goroutine per path, so the
  resequencer is shared. Start with one mutex, holding it across the in-order write to the
  TUN, which is what makes delivery order real. `bench_test.go` puts the whole receive
  path at ~100 ns, so at 30k pps one lock is expected to be fine. Stripe by bucket only if
  profiling says otherwise. Target under 500 ns per packet, with zero allocations in
  steady state.

## 8. Settings

New keys, every one with a working default, following `config.go`'s `Bounds` convention:

| Key | Default | Bounds | Meaning |
|---|---|---|---|
| `bulk_scheduler` | `cascade` | `cascade`, `flow` | Kill switch. `flow` is v0.1 exactly: per-flow spread and the D-031 gate |
| `cascade_queue_target_ms` | 40 | 5–1000 | Queue-delay target on unprotected paths |
| `cascade_protected_queue_ms` | 20 | 5–1000 | Queue-delay target on paths carrying real-time and transactional |
| `cascade_loss_percent` | 5 | 1–50 | Send-direction loss treated as congestion |
| `cascade_recover_intervals` | 5 | 1–1000 | Clean ticks before a cap grows (× 5 on protected paths) |
| `cascade_order_hysteresis_ms` | 10 | 0–500 | Delay margin before two members swap order |
| `cascade_report_interval_ms` | 200 | 50–5000 | Report cadence while receiving bulk |
| `resequencer_hold_margin_ms` | 10 | 0–500 | Added to the measured delay spread |
| `resequencer_max_hold_ms` | 200 | 20–2000 | Hard cap on the hold, and the basis of the delta gate |

- **`admission_queue_delay_ms` and `admission_recover_intervals`** stay, and apply only in
  `flow` mode. D-031's code is deleted together with `flow` mode, once v0.2 has been
  validated on the road. Until then `flow` must be a faithful v0.1, or the kill switch
  would not be a way back.
- **Flipping the switch** takes effect on the next tick through the existing hot reload
  (`config.Holder.Watch`), with no restart. The operator's recovery for "calls got worse
  after the update" is one setting in the UI.

## 9. Observability

It follows the existing pattern: flat fields in `state.Snapshot`, one writer (D-032), the
same numbers exported to Prometheus, and transitions only in the log.

- **Per path.** `cascade_position` (−1 when not a member), `cascade_protected`,
  `bulk_cap_kbps` (0 = unlimited), `bulk_kbps`, and `bulk_throttled` (bool, cap binding
  this tick).
- **Session.** `bulk_scheduler` (the mode actually in force, with the reason when
  `cascade` is configured but inactive, e.g. "peer is wire version 2"), `bulk_throttled_drops`,
  `resequencer_hold_ms`, `resequencer_buffered`, `resequencer_buckets_active`,
  `resequencer_gaps_skipped` and `resequencer_late_delivered`.
- **UI.** One "Bulk" tile showing the order, each member's cap and rate, and resequencer
  health. It says plainly when cascade is configured but not active, and why.

## 10. Tests

Each must fail when the behaviour it names is removed. That is the project's standard
(D-033, D-038).

**Carried over from D-031**, now against the controller:

- `TestBulkStarvedWhenTheCallsPathIsQueueing` becomes: the protected path's cap falls
  toward the floor while its queue sits over the protected target.
- `TestBulkReadmittedOnlyAfterTheQueueStaysClear` becomes: a protected cap does not grow
  until 5 × `cascade_recover_intervals` clean ticks.
- `TestAdmissionDisabledWithoutClassification` becomes: no cascade, no caps and no drops
  when the classifier is not running. Likewise in blind mode, and toward a v2 peer.

**New, scheduler:**

- Order is by outbound delay descending, with protected paths always last.
- Order does not swap inside the hysteresis margin.
- The first member takes all bulk while its cap is unlimited.
- Spill happens only after congestion on the member ahead.
- The N-path cascade with two paths behaves exactly as a two-path design would.
- A loss-only congestion signal caps a path that never queues (D-046's link).
- A cap grows only when demand-limited.
- The delta gate excludes a path too slow to resequence.
- Forest canopy: with no unprotected member, the D-033 path takes the first slot.
- Transactional rides the primary alone in cascade mode.
- `bulk_scheduler: flow` reproduces v0.1's `txFor` decisions exactly.

**New, wire:**

- v2↔v3 negotiation settles on v2 at both ends, and v3↔v3 settles on v3 (§3 item 6).
- The flow-seq field is present exactly on v3 bulk data packets.
- The auth tag covers the field.
- `MaxDataHeaderLen` and the recommended MTU arithmetic come out at 1288.

**New, resequencer:**

- In-order passthrough.
- Reorder within budget is delivered in order.
- A gap is skipped at the budget.
- A late packet after a skip is delivered, not dropped.
- 20-bit wraparound over thousands of packets, not a few (D-038's lesson).
- Sender restart reset.
- Memory bound force-skips and never drops.
- **Bucket isolation:** a gap in one bucket does not delay another.
- The hold budget follows the inbound spread and respects its clamps.
- Duplicated real-time packets never enter it.
- Benchmark: per-packet cost and allocations.

**Integration, network namespaces** (as in D-042):

- **Setup:** two veth paths with netem at 20 ms and 80 ms of RTT, 1% loss on one, and
  rate limits.
- **Pass criteria:**
  - A single-flow iperf3 beats the best single path.
  - A synthetic 50 pps RTP stream on the protected path keeps its jitter and loss within
    noise of an idle run while bulk is overflowing onto that path.
  - Protected-cap throttle transitions do not oscillate within a tick.

## 11. Implementation order

Each step builds, passes `go vet` and `go test ./...` (check the exit code, not grepped
output), and is deployable on its own.

1. **Wire v3 groundwork, no behaviour change.**
   - Versioned capability (§4.1).
   - Flow-seq field parse and emit (§4.2), sender stamping on bulk.
   - `MaxDataHeaderLen` + 4 and `dedupBits` 65536.
   - Deploy home first, then the RV, with both units changed to `-tun-mtu 1288`.
   - Verify "peer speaks wire version 3" in both logs and a clean tunnel.
2. **Resequencer.** Enabled on receipt of flow-seq packets. The sender is still in flow
   mode, so traffic arrives in order and this is a live canary: `gaps_skipped` and
   `late_delivered` must stay at zero under a real download.
3. **Report cadence while receiving bulk** (§6).
4. **Cascade membership, order, controller and data-path buckets** (§5), behind
   `bulk_scheduler`. Transactional back to the primary in cascade mode.
5. **Observability and UI** (§9).
6. **Network-namespace integration test** (§10), then deploy with `cascade` as the
   default. Standing approval covers the nodes.
7. **Road tuning** (§13), then record what was built and measured in `decisions.md` as new
   D-entries, and rename "v1"/"v2" in the older documents.

## 12. After the scheduler: v0.1 gaps v0.2 also closes

Recorded here so they are not lost. Ordered by reliability impact, not yet designed:

1. **Home endpoint is hardcoded.** `Endpoint = 162.231.243.253:48219` in the RV's
   `wg1.conf`/`wg2.conf`, and WireGuard does not re-resolve. A home IP change is a dead
   tunnel with no automatic recovery. Needs dynamic DNS plus re-resolution with a cached
   last-known-good address (`scope-v1.md`, "Reaching home").
2. **Out-of-band demotion is not wired.** `machine.demote` exists and nothing calls it:
   Starlink obstruction telemetry and ModemManager RSRP/SINR (D-017).
3. **`canCarry` ignores `haveCeiling`**, so a path at 100% loss with a zero ceiling is
   still a duplication target (D-051).
4. **Captive portal detection**, needed once campground Wi-Fi is a link.
5. **Provisioning bundle** (D-014), including the D-025 auth key.
6. **Vendor prefix feed.** `Classifier.SetVendorPrefixes` has no caller.
7. **Persistence across reboots** of path reputation, flap history and learned MTU.
8. **TUN MTU tracks the daemon's recommendation** instead of a flag (D-029).

## 13. Road tuning checklist

Every default in §5 and §8 is reasoned, not measured. On the road, from
`/var/lib/openmultipath/history.jsonl` and the UI:

- **Protected path during a call with a download running.** Does queue delay stay under
  `cascade_protected_queue_ms`, and does call quality (R/MOS) hold? If not, lower the
  target before touching anything else.
- **Throughput.** Does single-flow throughput exceed the best single link when both links
  are healthy? If caps grow too slowly, the ×1.10 growth constant is the lever.
- **Resequencer.** `late_delivered` persistently above zero means
  `resequencer_hold_margin_ms` is too small. `resequencer_hold_ms` sitting at the maximum
  means a path belongs outside the delta gate.
- **Loss.** Are healthy cellular links being capped by `cascade_loss_percent`? Look for
  `bulk_throttled` on a path with low queue delay.
- **Order.** Order swaps per hour. More than a handful means raising
  `cascade_order_hysteresis_ms`.
- **Canyon and canopy transitions.** Check them against `scope-v1.md`'s walkthrough, which
  remains the behavioural spec.

## 15. As built (2026-09-12)

Built in one session, tested in a network-namespace lab and on the two real nodes, and left
running in cascade mode. Everything below changed during implementation, each for a reason
measured rather than argued. The code comments carry the full reasoning next to each rule.

### What the owner added

- **S12.** Real-time on a path changes its place in bulk's fill order and nothing else.
  This removed, from cascade mode:
  - the lower queue target on the call's path (`cascade_protected_queue_ms` is gone);
  - the five-times-slower recovery there;
  - a "walk bulk onto the call's path" bound;
  - every ingress drop tied to the call.

  §5.4's per-path controller is identical on every path. D-031's gate remains in `flow`
  mode only.

### Wire (§4)

- **Versioned capability** is built as designed, and was verified live: a v0.2 home talking
  to a v0.1 vehicle settled on version 2, and the tunnel stayed up through the rolling
  upgrade.
- **Report entries are 16 bytes in v3, not 14.** A third new figure, the peer's
  **receive rate per path** over the last second (`RxKbpsBy16`), is added. A sender can only
  count what it put in; while a link's buffer absorbs a burst without loss, "sent minus
  loss" reads high exactly when the link is full. That hid every BBR probe from the
  controller in the lab.
- The MTU arithmetic is unchanged: **1288**, and both units now pass `-tun-mtu 1288`.

### Resequencer (§7)

- **Loss is detected, not waited out.** Paths keep their own packets in order, so a gap
  that every path carrying the flow has delivered past is lost and skipped at once. For
  the first second of a flow, any path carrying spread bulk also counts, so a slow path
  new to the flow is waited for.
- **The hold is also measured.** It is the larger of the predicted delay spread and 1.25×
  the longest gap observed to fill (or to arrive late) over the last 2–4 s. The prediction
  alone understates: a path's round trip comes back on whichever path carries the echo,
  so halving it does not give that path's one-way delay. In the lab the prediction held
  26 ms against a real 30 ms and thousands of packets arrived late.
- **Every live path counts toward the predicted hold,** not only paths already carrying
  bulk, so the hold is right before spilling starts.

### Cascade (§5)

- **Membership is not-down, not-flapping, R ≥ `spread_min_r`, not red, and not undersized.**
  - "Stable" is not required: a queue our own bulk built made the state machine call the
    link we were filling unstable.
  - Flapping paths are excluded, and **there is no forest-canopy fallback**. A flapping
    Starlink put first in line took a real upload from 68 Mbit/s to 0.1. Spread per packet,
    a flapping link stalls every flow it touches.
  - **The size gate's bar includes the call's path.** Left out, the vehicle's ~3 Mbit
    Starlink tier was compared only with itself and filled ahead of a ~55 Mbit AT&T link.
- **Order and the delta gate use base delay (half the RTT floor),** not the scoring delay.
  The scoring delay carries the p95 tail of our own queue, so the cascade would chase its
  own queue and drop links for minutes. The owner's "measured outbound latency" (S5) is
  kept in that form.
- **Nothing is dropped.**
  - Allowances decide the split, not the total. Past every allowance, bulk goes to the
    **first path in fill order**.
  - Dropping there made the tunnel a policer. TCP never pushed past the first link, and a
    two-link cascade carried less than flow placement.
  - Sending the overflow to the least-queued path instead put it on the call's path, where
    the lab measured 116–166 ms audio gaps. The first path in order kept calls clean with
    more throughput.
- **Controller additions to §5.4:**
  - **Thin-load guard:** a path sending under `bw_min_load_kbps` has its queue and loss
    readings ignored. Idle Starlink read 8.6 / 24.6 / 64.7 ms of standing queue at
    median / p90 / max with no load, and cut idle links to the floor.
  - **Confirmation:** a cut needs two consecutive evaluations over the line.
  - **Drain grace:** no second cut for 2 s while the queue is already shrinking.
  - **Trim:** while a standing queue above 5 ms is rising, the cap follows what is
    delivered.
  - **Peak bound:** after a path's first congestion, its cap is at most 1.1× the best rate
    it delivered over 1–2 s. This lets BBR's probes spill, so BBR aggregates.
  - **Growth:** on packets turned away (exhaustion) as well as on running near the cap,
    at ×1.3 per evaluation while under half the rate of the last cut and ×1.1 above it.
  - **Blameless cuts:** a cut made with almost no bulk on the path is forgotten once the
    path is clean.
  - **Buckets** hold 10 ms of allowance, so short probes spill rather than hide.

### Still to tune on the road

- **Late packets at the resequencer.** With overflow to the first path, a loss-based
  sender can build a queue on it beyond the 200 ms hold cap. They are fail-open and
  counted (`resequencer.late`), but reordering costs TCP retransmits.
- **Starlink's standing-queue noise under load.** The thin-load guard only helps while a
  path is idle; the loaded readings still need a look.
- **The echo return-leg quirk.** A path's RTT includes the return leg of whichever path
  carried the echo. It predates v0.2 and biases every "half the round trip" figure.
- **The controller constants** in `cascade.go`, every one reasoned from one lab and one
  evening of real links.
